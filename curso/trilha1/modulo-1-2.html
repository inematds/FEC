T1 / Módulo 1.2

Tokens, custo e limites práticos por modelo

GA ~55 min 2.600 palavras eng. produto

Objetivo de aprendizagem

Ao final, você consegue (a) estimar custo de uma chamada antes de fazê-la, com erro <15%; (b) escolher entre frontier / low-cost / OSS para um caso dado; (c) usar prompt caching para reduzir custo em cenários de prefixo estável. Verificado em exercicios/modulo-1-2/test.py.

Tokens não são palavras

Cada provedor tem um tokenizer próprio. "engenharia de contexto" pode virar 5 tokens em um modelo Anthropic e 7 em outro. Heurísticas universais ("1 token ≈ 4 caracteres em inglês") erram bastante em PT-BR, em código, em emoji, e em qualquer texto técnico denso. Para estimar custo com confiança, você usa o tokenizer real do provedor (via SDK).

Os três níveis de modelo (e quando usar cada)

Tabela 1 — Categorias de modelo na FEC (PLAN seção 6, modelos pinados em evals/v1/models.json).
Categoria Custo relativo Janela típica Quando usar
Frontier $3-15 / M tokens 200k+ Raciocínio complexo, multi-passo, tarefas que exigem capacidade.
Low-cost (mini) $0.10-0.30 / M 128k+ Volume alto, classificação, extração, tarefas estruturadas.
OSS local $0 (custo de hardware) 8-32k confiável Privacidade, sem rede, custo zero por chamada, latência local.

Janela nominal vs. janela efetiva

"200k tokens" no marketing significa "o modelo aceita 200k tokens de input sem erro de API". Não significa "o modelo usa 200k tokens com a mesma qualidade". O benchmark RULER (Hsieh et al. 2024) mede janela efetiva: muitos modelos com 128k nominal degradam significativamente acima de 32-64k. Antes de assumir que cabe e funciona, mensure no harness.

Evidência: RULER reports + replicação interna em evals/v1/runs/effective-context-2026-04/.

Sub-tópicos

1Como contar tokens (sem chamar a API)

O que é

Cada SDK expõe um count_tokens (ou tokenizer) local. anthropic.client.messages.count_tokens(), tiktoken da OpenAI, etc.

Por que aprender

Você pode estimar custo localmente antes de mandar. Sem isso, planejamento de orçamento é chute.

Conceitos-chave

tokenizer offline, BPE pré-treinado, count vs. encode.

2Custo input vs. output (cuidado com a ratio)

O que é

Output tokens são tipicamente 3-5× mais caros que input. Mas em janelas longas, você paga mais em input total.

Por que aprender

Otimização incorreta — tentar reduzir output enquanto a janela está inflada — não move custo.

Conceitos-chave

Pricing tier, ratio i/o, batch discounts.

3Prompt caching: como obter desconto real

O que é

Anthropic e OpenAI oferecem cache de prefixo. Tokens cacheados custam ~10% do preço normal de input.

Por que aprender

Em chat com system prompt + few-shot grandes, cache pode reduzir custo de input em 80-90%. Detalhado em T5.2.

Conceitos-chave

Cache breakpoint, TTL, hit rate, prefix stability.

4Latência: prefill vs. decode

O que é

Prefill é o tempo para o modelo "ler" o input. Decode é o tempo para gerar tokens. Janela longa = prefill longo.

Por que aprender

Para UX de chat ao vivo, prefill domina o "tempo até primeiro token". Cache reduz drasticamente.

Conceitos-chave

TTFT (time to first token), tokens/sec, KV cache reuse.

5Limites por janela: quando cair para low-cost ou OSS

O que é

Heurística: se a tarefa é estruturada e o input cabe em <8k tokens, low-cost ou OSS tipicamente bastam. Frontier é para raciocínio complexo OU contexto realmente grande.

Por que aprender

Engenheiros pulam direto para frontier por inércia. Em volume, isso queima orçamento.

Conceitos-chave

Capability vs. context vs. cost, model routing.

6OSS local: matriz de hardware

O que é

Qwen2.5-7B em q4 cabe em 16GB RAM. Llama-3.1-8B-instruct também. Modelos >13B começam a exigir GPU. Ver OLLAMA-MATRIZ.md.

Por que aprender

O caminho gratuito do curso usa OSS — entenda o que cabe na sua máquina antes de tentar T4.3.

Conceitos-chave

Quantização (q4, q5, q8), tamanho VRAM/RAM, throughput CPU vs. GPU.

Quando NÃO otimizar custo

  • Quando a chamada é única ou rara: custo total é trivial; gaste seu tempo em qualidade, não em centavos.
  • Em prototipagem inicial: use frontier para estabelecer o teto de qualidade; otimizar depois.
  • Quando otimização frita qualidade: se trocar para low-cost cai groundedness em 20% mas reduz custo em 30%, você não está economizando.

Exemplo: estimar custo antes de chamar

from fec_sdk import check_compat

check_compat("modulo-1-2", expected_sdk_version=">=1.0,<2.0")

# Sem chamar a API: estimativa por tokenizer local.
# (Implementação completa em exemplos/modulo-1-2/estimar.py)

system_prompt = "Você é um assistente conciso." * 1
user_query = "Resuma este texto em 3 bullets."
contexto = open("documento.txt").read()  # exemplo

# Aproximação grosseira para PT-BR: ~3 chars/token. Tokenizer real do provedor é melhor.
tokens_est = (len(system_prompt) + len(user_query) + len(contexto)) // 3
custo_input  = tokens_est * 3.00 / 1_000_000   # $3 / M (frontier hipotético)
custo_output = 200 * 15.00 / 1_000_000          # 200 tokens de saída × $15/M

print(f"Estimado: ~{tokens_est} tokens input → ${custo_input + custo_output:.4f}")

Para tokenizador real, ver exemplos/modulo-1-2/estimar.py (usa adapter do provedor).
